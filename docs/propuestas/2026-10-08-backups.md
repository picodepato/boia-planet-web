# Copias de seguridad diarias de Supabase

Plan 019 T223, reunión del 2026-10-08 (decisión 17: «copias de seguridad
automáticas y periódicas»). El plan gratuito de Supabase no guarda copias, así
que las hace un flujo de GitHub Actions:
[`.github/workflows/supabase-backup.yml`](../../.github/workflows/supabase-backup.yml).

## Qué hace

- Cada día a las 02:41 UTC (y cuando se lanza a mano desde la pestaña
  **Actions → supabase-backup → Run workflow**).
- Vuelca la base de datos con `pg_dump` (cliente 17) en tres archivos:
  - `schema.sql`: tablas, funciones, políticas y permisos de `public` y
    `private`;
  - `data.sql`: los datos de `public` y `private` (eventos, Carnets, sellos,
    puntos, botellas, Las Calitas, auditoría…);
  - `auth.sql`: las cuentas (`auth.users`, `auth.identities` y
    `auth.mfa_factors`: email y TOTP del equipo).
- Comprueba cada archivo con `SHA256SUMS`, los empaqueta y los **cifra** con
  GPG (AES-256). La copia lleva emails y datos de las cuentas: sin cifrar no
  se sube.
- Lo guarda como artefacto del flujo, `boia-backup-<fecha>.tar.gz.gpg`,
  **30 días**. Después GitHub lo borra solo.

Qué **no** va en la copia: los archivos de Storage (fotos de las islas, clips
de la Galería, imágenes de sellos) y la configuración de Supabase (Auth,
correo, cubos de Storage y sus políticas). Los cubos y sus políticas se crean
con las migraciones que los definen (`20261007100100_event_photos.sql`,
`20261008100400_gallery_clips.sql`); los archivos habría que copiarlos aparte.

## Ponerlo en marcha (Hernán)

1. En Supabase (`boia-planet-dev`): **Project Settings → Database →
   Connection string**, pestaña **Session pooler** (puerto **5432**). Copia la
   cadena (`postgresql://postgres.<ref>:<contraseña>@aws-0-<región>.pooler.supabase.com:5432/postgres`)
   y pon la contraseña de la base de datos en su sitio.
   - No sirve la conexión directa (`db.<ref>.supabase.co`): es sólo IPv6 y los
     servidores de GitHub no tienen IPv6.
   - No sirve el «Transaction pooler» (puerto 6543): `pg_dump` necesita una
     sesión.
2. En GitHub: **Settings → Secrets and variables → Actions → New repository
   secret**, dos secretos:
   - `SUPABASE_DB_URL`: la cadena del paso 1.
   - `BACKUP_PASSPHRASE`: una frase larga (por ejemplo, 6 palabras al azar).
     Guárdala también fuera de GitHub (gestor de contraseñas): **sin ella la
     copia no se puede abrir**, y GitHub no deja volver a leer un secreto.
3. **Actions → supabase-backup → Run workflow** para probarlo. Tiene que
   acabar en verde y dejar un artefacto `boia-backup-…`.
4. Los flujos programados de GitHub se paran solos si el repositorio pasa 60
   días sin actividad: si eso pasa, GitHub avisa por email y basta con
   volver a activarlo en la pestaña **Actions**.

Si falta un secreto, el flujo falla en el primer paso con «Falta el secreto
…» y no vuelca nada.

## Descargar una copia

- Web: **Actions → supabase-backup →** la ejecución del día **→ Artifacts →
  boia-backup-…** (descarga un `.zip` con el `.tar.gz.gpg` dentro).
- Con la CLI de GitHub: `gh run list --workflow supabase-backup.yml` y
  `gh run download <id de la ejecución>`.

Abrirla (pide la frase de `BACKUP_PASSPHRASE`):

```sh
unzip boia-backup-2026-10-09T0241Z.zip
gpg --output copia.tar.gz --decrypt boia-backup-2026-10-09T0241Z.tar.gz.gpg
tar -xzf copia.tar.gz
cd boia-backup-2026-10-09T0241Z
sha256sum -c SHA256SUMS   # los tres archivos, «OK»
```

## Restaurar

Siempre en un proyecto Supabase **nuevo y vacío** (nunca encima del que está
en uso: si algo sale mal, el de antes sigue ahí). Hace falta `psql` 17.

1. Crea el proyecto y copia su cadena del **Session pooler** (como arriba) en
   `NEW_DB_URL`.
2. Carga esquema, cuentas y datos de una vez. Con
   `session_replication_role = replica` no saltan los disparadores (auditoría,
   saldos, versiones): los datos entran tal como estaban.

   ```sh
   psql --single-transaction --variable ON_ERROR_STOP=1 \
     --file schema.sql \
     --command 'SET session_replication_role = replica' \
     --file auth.sql \
     --file data.sql \
     --dbname "$NEW_DB_URL"
   ```

   Si falla, no queda nada a medias (una sola transacción): se lee el error,
   se corrige y se repite.
3. Vuelve a crear los cubos de Storage y sus políticas (las partes de
   Storage de las dos migraciones de arriba) y sube los archivos si los
   tienes aparte.
4. En el proyecto nuevo, configura Auth como el anterior (correo con código de
   6 cifras, TOTP) y cambia en Vercel `NEXT_PUBLIC_SUPABASE_URL` y
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` (y en GitHub `SUPABASE_DB_URL`) a los del
   proyecto nuevo.

Probar una restauración de vez en cuando (por ejemplo, una vez al mes, en un
proyecto de pruebas que luego se borra) es la única forma de saber que las
copias sirven.
