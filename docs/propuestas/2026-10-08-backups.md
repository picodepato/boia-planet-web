# Copias de seguridad diarias de Supabase

Plan 019 T223, reunión del 2026-10-08 (decisión 17: «copias de seguridad
automáticas y periódicas»). El plan gratuito de Supabase no guarda copias, así
que las hace un flujo de GitHub Actions:
[`.github/workflows/supabase-backup.yml`](../../.github/workflows/supabase-backup.yml).

## Qué hace

- Cada día a las 02:41 UTC (y cuando se lanza a mano desde la pestaña
  **Actions → supabase-backup → Run workflow**).
- Vuelca la base de datos con `pg_dump` (cliente 17) en tres archivos:
  - `schema.sql`: tablas, funciones, políticas y permisos de `public` y
    `private`;
  - `data.sql`: los datos de `public` y `private` (eventos, Carnets, sellos,
    puntos, botellas, Las Calitas, auditoría…);
  - `auth.sql`: las cuentas (`auth.users`, `auth.identities` y
    `auth.mfa_factors`: email y TOTP del equipo).
- Copia los **archivos de Storage** (plan 020 T230): fotos de las islas
  (`event-photos`), clips de la Galería (`event-clips`) e imágenes de los
  sellos (`stamp-images`). La lista sale de la base (`storage.objects`, en
  `storage.json`) y cada archivo se baja de su URL pública a
  `storage/<cubo>/<ruta>` (lo hace `.github/scripts/storage-backup.py`).
- Comprueba cada archivo (también los de Storage) con `SHA256SUMS`, los
  empaqueta y los **cifra** con GPG (AES-256), todo junto. La copia lleva
  emails y datos de las cuentas: sin cifrar no se sube.
- Lo guarda como artefacto del flujo, `boia-backup-<fecha>.tar.gz.gpg`,
  **30 días**. Después GitHub lo borra solo.
- **Purga la papelera de 30 días** (plan 020 T230, decisión 6), después de
  guardar la copia: los socios y las fiestas que llevan más de 30 días
  borrados en el Admin se borran de verdad (`select
  public.purge_expired_trash()`). El plan gratuito de Supabase no garantiza
  `pg_cron`, así que la purga diaria va aquí. Una fiesta que alguien tiene en
  su historial (su sello, una compra) no se borra: se queda oculta. Si la
  migración `20261008200200_member_party_trash.sql` aún no está aplicada, el
  paso avisa y no hace nada. El Admin también purga lo caducado al borrar o
  devolver algo y con «Purgar lo caducado» de la Papelera.

Qué **no** va en la copia: la configuración de Supabase (Auth, correo, cubos
de Storage y sus políticas). Los cubos y sus políticas se crean con las
migraciones que los definen (`20261003100600_admin_real.sql`,
`20261007100100_event_photos.sql`, `20261008100400_gallery_clips.sql`).

Tamaño: cada copia lleva todos los archivos de Storage (los clips pesan hasta
20 MB cada uno). GitHub guarda gratis un espacio limitado de artefactos por
cuenta (en un repositorio privado del plan gratuito, 500 MB entre todos los
artefactos guardados): con muchos clips, mira en **Settings → Billing**
cuánto ocupa y, si hace falta, baja `retention-days` en el flujo.

## Ponerlo en marcha (Hernán)

1. En Supabase (`boia-planet-dev`): **Project Settings → Database →
   Connection string**, pestaña **Session pooler** (puerto **5432**). Copia la
   cadena (`postgresql://postgres.<ref>:<contraseña>@aws-0-<región>.pooler.supabase.com:5432/postgres`)
   y pon la contraseña de la base de datos en su sitio.
   - No sirve la conexión directa (`db.<ref>.supabase.co`): es sólo IPv6 y los
     servidores de GitHub no tienen IPv6.
   - No sirve el «Transaction pooler» (puerto 6543): `pg_dump` necesita una
     sesión.
2. En GitHub: **Settings → Secrets and variables → Actions → New repository
   secret**, dos secretos:
   - `SUPABASE_DB_URL`: la cadena del paso 1.
   - `BACKUP_PASSPHRASE`: una frase larga (por ejemplo, 6 palabras al azar).
     Guárdala también fuera de GitHub (gestor de contraseñas): **sin ella la
     copia no se puede abrir**, y GitHub no deja volver a leer un secreto.

   Para los archivos de Storage no hace falta nada más: la URL del proyecto
   sale del usuario de la cadena del paso 1 (`postgres.<ref>`). Sólo si no
   saliera (el paso falla con «No sale la URL del proyecto…»), añade en la
   pestaña **Variables** del mismo sitio la variable `SUPABASE_URL` con
   `https://<ref>.supabase.co`. Los tres cubos de la web son públicos; si un
   día se crea uno privado, el flujo falla con «Cubos privados sin copia» y
   habrá que darle al flujo una clave de servicio para bajarlo (no está
   hecho: hoy no hay ninguno).
3. **Actions → supabase-backup → Run workflow** para probarlo. Tiene que
   acabar en verde y dejar un artefacto `boia-backup-…`.
4. Los flujos programados de GitHub se paran solos si el repositorio pasa 60
   días sin actividad: si eso pasa, GitHub avisa por email y basta con
   volver a activarlo en la pestaña **Actions**.

Si falta un secreto, el flujo falla en el primer paso con «Falta el secreto
…» y no vuelca nada.

## Descargar una copia

- Web: **Actions → supabase-backup →** la ejecución del día **→ Artifacts →
  boia-backup-…** (descarga un `.zip` con el `.tar.gz.gpg` dentro).
- Con la CLI de GitHub: `gh run list --workflow supabase-backup.yml` y
  `gh run download <id de la ejecución>`.

Abrirla (pide la frase de `BACKUP_PASSPHRASE`):

```sh
unzip boia-backup-2026-10-09T0241Z.zip
gpg --output copia.tar.gz --decrypt boia-backup-2026-10-09T0241Z.tar.gz.gpg
tar -xzf copia.tar.gz
cd boia-backup-2026-10-09T0241Z
sha256sum -c SHA256SUMS   # los .sql, storage.json y los archivos de storage/, «OK»
```

## Restaurar

Siempre en un proyecto Supabase **nuevo y vacío** (nunca encima del que está
en uso: si algo sale mal, el de antes sigue ahí). Hay dos caminos; el primero
es el que se probó (plan 032 T302, abajo).

### Camino A: `tools/backup/restore.mjs` (Node, sin `psql`)

Hace todo en orden y se para al primer fallo: descifra, comprueba
`SHA256SUMS`, carga `schema.sql` (si el destino es nuevo), `auth.sql` y
`data.sql` en **una sola transacción** (con `session_replication_role =
replica`, así no saltan auditoría, saldos ni versiones: los datos entran tal
como estaban), sube `storage/<cubo>/<ruta>` por la API de Storage y, al final,
cuenta filas por tabla y archivos de Storage y los compara con la copia (y
bajan tres archivos para comparar su SHA-256). Sale con 1 si algo no cuadra.
Se niega a tocar el proyecto de producción y a cargar sobre un destino con
datos.

1. Descarga la copia (arriba) y ten a mano la frase `BACKUP_PASSPHRASE`.
2. Crea el proyecto Supabase nuevo. Apunta su URL, su clave de servicio
   (`service_role`, **Project Settings → API Keys**) y la cadena del Session
   pooler en un archivo `.env` **fuera del repositorio**:

   ```
   NEXT_PUBLIC_SUPABASE_URL=https://<ref nuevo>.supabase.co
   SUPABASE_SERVICE_ROLE_KEY=...
   SUPABASE_DB_URL=postgresql://postgres.<ref nuevo>:<contraseña>@aws-0-<región>.pooler.supabase.com:5432/postgres
   ```
3. **Primero las migraciones.** Los cubos de Storage (y sus políticas) no
   salen en la copia: los crean las migraciones, igual que el esquema de la
   web. Aplica al proyecto nuevo las mismas que ya tiene el de antes, con la
   CLI de Supabase (`supabase db push`), **sin semillas**. (`pnpm
   db:migrate:dev` también las aplica, pero añade las semillas de muestra:
   sólo para desarrollo.) Las migraciones dejan algunas filas de ajustes
   (`site_settings`…): no es problema, el paso siguiente las sustituye por las
   de la copia.
4. Restaura. Con el esquema ya puesto se usa `--skip-schema`:

   ```sh
   BACKUP_PASSPHRASE='…' node tools/backup/restore.mjs \
     boia-backup-2026-10-09T0241Z.tar.gz.gpg --env /ruta/al/.env --skip-schema
   ```

   (Sin `BACKUP_PASSPHRASE` en el entorno, GPG pregunta la frase.) Antes de
   tocar nada lee y comprueba la copia entera (SHA256SUMS) y mira el destino:
   se niega si ya tiene cuentas o archivos de Storage (un proyecto en uso), si
   faltan los cubos o si es el de producción. El archivo `--env` manda sobre
   las variables del shell, y el programa dice de dónde sacó la conexión.
   Termina con `restore: todo bien`. Si el proyecto no tiene migraciones
   (sólo `public` y `private` vacíos) y la copia trae `schema.sql`, puede
   cargarlo él (sin `--skip-schema`), pero entonces los cubos de Storage no
   existen y habrá que crearlos antes de subir los archivos: el camino con
   migraciones es el probado.
5. Las URL públicas guardadas en los datos (`stamp_image_url`, fotos, clips)
   llevan el dominio del proyecto viejo: cámbialas al nuevo con un `update …
   set … = replace(…, '<ref viejo>', '<ref nuevo>')` en las columnas que las
   guardan.
6. Configura Auth como el anterior (correo con código de 6 cifras, TOTP) y
   cambia en Vercel y en Cloudflare `NEXT_PUBLIC_SUPABASE_URL` y
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` (y en GitHub `SUPABASE_DB_URL`) a los del
   proyecto nuevo. Después de desplegar, `pnpm check:hosts <url pública>
   <url copia>` comprueba que los dos hosts siguen en el mismo modo de cuentas
   y con el mismo proyecto.
7. Una copia vieja puede traer contenido que después se retiró (REQ-ARQ-013):
   tras restaurar, repasa en el Admin las fiestas y los socios que estaban en
   la Papelera y vuelve a purgar con «Purgar lo caducado».

### Camino B: `psql` (a mano)

Hace falta `psql` 17.

```sh
psql --single-transaction --variable ON_ERROR_STOP=1 \
  --file schema.sql \
  --command 'SET session_replication_role = replica' \
  --file auth.sql \
  --file data.sql \
  --dbname "$NEW_DB_URL"
```

Antes, quita de `schema.sql` la línea `CREATE SCHEMA public;` (ya existe en un
proyecto Supabase nuevo y `psql` pararía; `restore.mjs` la quita solo). Un
`pg_dump` 17.6 o más nuevo (el del flujo) escribe además líneas `\restrict
<clave>` y `\unrestrict <clave>`: `psql` 17.6+ las entiende, uno anterior
no (bórralas). Si falla, no queda nada a medias. Los archivos de Storage se suben después,
desde el panel de Supabase (**Storage → el cubo → Upload**) o con la CLI, y se
repiten los pasos 5 y 6 de arriba.

## Probar la restauración (sin tocar producción)

Probar una restauración de vez en cuando (por ejemplo, una vez al mes, en un
proyecto de pruebas que luego se borra) es la única forma de saber que las
copias sirven. Para ensayar sin esperar a una copia del flujo, sobre el
proyecto de desarrollo (`boia-planet-dev`, nunca producción), con su
`apps/web/.env.local`:

```sh
node tools/backup/counts.mjs > antes.json                     # filas y archivos antes
BACKUP_PASSPHRASE='…' node tools/backup/dump.mjs --out ../copias-dev --encrypt
BACKUP_PASSPHRASE='…' node tools/backup/restore.mjs ../copias-dev/boia-backup-….tar.gz.gpg \
  --skip-schema --wipe --confirm-ref <ref de dev>             # vacía y restaura
node tools/backup/counts.mjs > despues.json
node tools/backup/counts.mjs --diff antes.json despues.json   # «iguales: …»
pnpm db:migrate:dev && pnpm test:supabase                     # dev sigue sano
```

`dump.mjs` hace la copia con Node, con el mismo formato que el flujo pero sin
`schema.sql`. La copia lleva emails: guárdala **fuera del repositorio**.
Los números de la prueba que se hizo (plan 032 T302) están en `ESTADO.md`.
